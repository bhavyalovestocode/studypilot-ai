# StudyPilot AI — Version 1 Product Review

**Review date:** 2026-10-19  
**Scope:** Current repository implementation only. No application code was changed during this audit.

## Executive summary

StudyPilot AI has a clear, visually coherent setup-to-checklist concept. The landing form asks for the three inputs required to create a plan, the API validates and constrains provider output, and the dashboard includes useful completion, timer, export, and rebalance affordances. The strongest evidence is technical: the core state model and route tests exist, and lint, production build, and the existing test suite pass.

Version 1 is not yet a dependable end-to-end study product. The roadmap is generated by an external provider but there is no persisted server-side plan or account, so progress is browser-local and device-specific. Rebalancing is a client-only redistribution algorithm that can overload the final day and does not visibly explain the resulting schedule. The generated plan is not verified against the requested dates or daily capacity after the provider responds. Most importantly, a valid browser workflow reached a `502` AI-service response in this environment, so the primary value proposition could not be completed in the live check.

The recommended Version 2 focus is reliability and trust: make generation recoverable and transparent, make progress portable, and make adaptive scheduling capacity-aware and user-confirmable before adding more decorative features.

### Implemented data model

The client model is:

- `RoadmapDay`: `day`, ISO-like `date`, and three required arrays: `theoryTopics`, `exercises`, and `practiceQuestions`.
- `StudyTask`: `id`, `title`, `subject`, `estimatedMinutes`, and `completed`.
- `ProgressSummary`: total tasks, completed tasks, and a rounded percentage.

The API repeats this shape and validates that each day has at least one item in each array. The client defensively normalizes provider data before rendering. This is a useful boundary, but it is not a complete domain validation layer: the API does not verify day sequence, date range, unique IDs, or per-day minute totals.

### Persistence and adaptive scheduling

- The full normalized roadmap is written to `localStorage` under `studypilot-roadmap`.
- The exam date is stored separately under `studypilot-exam-date`.
- Completed full-day dates are stored under `studypilot-streak`.
- There is no server persistence, user identity, sync, backup, migration version, or explicit “saved” indicator.
- “Rebalance” collects unfinished tasks, preserves completed tasks in their existing days, and appends unfinished tasks into available day capacity. It runs after a fixed 650 ms timeout to simulate work.
- Rebalance does not call the API, change the exam date, add days, or ask the student to approve a preview. Remaining tasks are forced onto the final roadmap day when they do not fit earlier days.

### States and accessibility observed

The setup flow has disabled-submit prevention, a date error, loading text/status, retry text, and an alert region. The dashboard has progress bars, status/alert messages, empty-roadmap copy, a focus timer, and a mobile navigation drawer.

Labels are associated with the main inputs, the checkbox is keyboard-operable despite being visually hidden, and the primary progress bar has ARIA values. However, the mobile drawer does not expose a dialog landmark or focus trap, the drawer close button has no accessible name, and several icon-only or visually implied controls depend on surrounding context. The browser console also reported a React hydration mismatch on the root `html` attributes, showing a `color-scheme` difference during theme initialization.

## 3. Heuristic evaluation

Severity uses **Critical**, **High**, **Medium**, and **Low** to describe user impact if the issue occurs.

### H1 — Visibility of system status

**Observed behavior/evidence:** Generation exposes a spinner, disabled button, and live status in [page.tsx](../src/app/page.tsx). Rebalancing exposes a spinner and success/error text. Local persistence happens silently in an effect; there is no “saved locally” or “last synced” status.

**User problem:** A student cannot tell whether a plan is safely backed up, whether progress survived a browser/device change, or whether a long-running provider request is still healthy. The fixed retry path does not expose request duration or a next step beyond trying again.

**Severity:** High for persistence/reliability; Medium for loading feedback.

**Recommended improvement:** Add explicit save/sync state and a request timeout/cancel or retry-with-backoff experience. Show generation stages only when they reflect real work; otherwise show an honest elapsed-time state and a clear retry action.

**Validation test:** Start generation with a delayed/failing provider and verify that users can identify the current state, recover without duplicate plans, and understand whether progress is saved after reload.

### H2 — Error prevention and recovery

**Observed behavior/evidence:** The setup form prevents empty syllabus/date submission and constrains the date input to today or later. The API validates JSON, hours from 1–12, date format, valid dates, and past dates. Provider failures return safe generic errors. However, the generated response is not checked for requested date range, chronological day sequence, unique task IDs, or daily minute capacity.

**User problem:** A syntactically valid but semantically wrong AI plan can look trustworthy while omitting dates, duplicating tasks, exceeding available time, or placing work outside the exam window. A user who falls behind can receive a final-day overload from rebalance.

**Severity:** High.

**Recommended improvement:** Add domain validation after provider parsing: expected day count/range, unique IDs, non-negative and capacity-bounded totals, and a deterministic repair/retry path. For rebalance, calculate remaining capacity across the actual remaining days and show overflow before applying.

**Validation test:** Feed the route plans with duplicate IDs, wrong dates, over-capacity days, skipped days, and invalid task totals; assert rejection or repair. Seed a roadmap whose unfinished minutes exceed available capacity and verify the UI does not silently overload a day.

### H3 — Recognition rather than recall

**Observed behavior/evidence:** Labels, examples, character count, date control, hours slider, task-group labels, estimated minutes, “Today”, progress percentage, and quick explanation affordances reduce recall. The API prompt also requests concrete actionable tasks.

**User problem:** The form does not explain what makes a useful syllabus paste, how the daily-hours value affects the generated plan, or whether the exam date itself is a study day. On the dashboard, the student must infer how rebalance changes dates and capacity from a short paragraph.

**Severity:** Medium.

**Recommended improvement:** Add a short input example with expected granularity, a capacity preview (“about X minutes/day”), and a rebalance preview showing moved tasks, new dates, and any uncovered work.

**Validation test:** Give first-time students only the UI and measure input completion, invalid/underspecified syllabi, and ability to predict what “rebalance” will do before and after the copy/preview change.

### H4 — User control and freedom

**Observed behavior/evidence:** Students can create a new strategy, expand/collapse days, toggle tasks, reset the timer, switch work/break mode, print, and download an ICS calendar. Rebalance is immediate after a simulated delay; there is no undo or preview. Generation cannot be cancelled.

**User problem:** A mistaken check or rebalance requires manual reversal. A student may lose a preferred schedule arrangement and cannot compare alternatives. Starting a new strategy does not clearly warn that the currently displayed plan remains in local storage and can be replaced on the next successful generation.

**Severity:** Medium to High.

**Recommended improvement:** Add undo for task toggles/rebalance, a confirmable rebalance preview, and an explicit new-strategy flow that says what will happen to the current plan.

**Validation test:** Ask users to intentionally make and recover from a mistaken completion and rebalance. Success means they can recover without re-entering the syllabus and without losing completed work.

### H5 — Consistency and standards

**Observed behavior/evidence:** The app consistently uses button/input styles, labels, status color, and familiar calendar/download/print affordances. The model and provider schema consistently use three task groups. The README is still the default create-next-app guide and does not describe StudyPilot’s actual workflow, environment, or test commands.

**User problem:** Product documentation gives developers and evaluators an incorrect starting point. In the UI, “adaptive scheduling” implies a robust schedule model, while the implementation is a local heuristic with a forced overflow fallback.

**Severity:** Medium.

**Recommended improvement:** Replace the README with product-specific setup, environment-variable handling without secrets, workflow behavior, data/persistence limitations, and validation commands. Align “adaptive” copy with the current guarantee or strengthen the algorithm first.

**Validation test:** Have a new developer follow the documentation from clone to local validation without asking for missing steps; have a student describe what will happen after falling behind and compare that answer with actual behavior.

## 4. Core user journey evaluation

| Journey step | Current evidence | Assessment |
|---|---|---|
| 1. Enter syllabus | Controlled textarea, example placeholder, character count, label/help text. No length limit or syllabus parsing preview. | Good first input affordance; unclear quality boundary and no preview of how text was interpreted. |
| 2. Set exam date/hours | Native date input, min date, 1–12 hour slider, default 3 hours. API repeats bounds and rejects past dates. | Prevents common invalid values; hours are not converted into a visible plan capacity before generation. |
| 3. Generate roadmap | POST to `/api/generate-roadmap`; 30-second provider timeout and safe error classes; strict JSON shape. | Strong defensive API boundary, but live generation was blocked by 502 and semantic output checks are incomplete. |
| 4. Complete daily tasks | Checkbox toggles nested tasks and recalculates overall completion; task state is written to local storage. | Functional for one browser; no task-level timestamp, undo, daily completion confirmation, or server sync. |
| 5. Persist progress | Roadmap and streak dates restore from local storage on mount; malformed roadmap storage is removed. | Useful offline persistence, but private browsing/storage quota/device changes are not surfaced and errors are silently handled. |
| 6. Rebalance when behind | Client algorithm preserves completed tasks, fills days up to `dailyHours * 60`, then appends all overflow to the final day. | Core intent exists but the fallback can make the plan unrealistic; no preview, constraints report, or evidence that the exam date remains feasible. |

### Important journey gaps

1. **No successful end-to-end generation was available in the audit environment.** The provider path is a single dependency and there is no fixture/demo mode for product validation.
2. **The “today” concept is unstable across time zones.** The client uses UTC date strings and displays dates through local `Intl.DateTimeFormat`; users near midnight can see a different day than the scheduling logic.
3. **The dashboard chooses `roadmap[0]` as `activeDay`.** If a restored or generated roadmap starts later than today, the fallback “today’s focus” can point to the first planned day rather than the next actionable day.
4. **No empty generated roadmap is reachable through the normal UI.** The API allows `roadmap: []` when there are no study days, but the client treats an empty normalized roadmap as invalid. The `EmptyRoadmap` component is therefore defensive rather than a tested product state.
5. **Progress is task-count based, not time- or day-based.** Completing many short tasks can represent the same percentage as completing a few long tasks; this may not match a student’s perceived workload.

## 7. Recommended Version 2

### Selected improvements

1. **Reliable generation contract:** add fixture-backed end-to-end coverage, semantic roadmap validation, provider timeout/retry guidance, and a clear failure state that never implies a plan exists.
2. **Trustworthy persistence:** version the roadmap schema and provide durable sync or an explicit export/import recovery path. Show save status and preserve progress when regenerating where task identity can be matched.
3. **Safe adaptive scheduling:** calculate capacity over remaining days, preview all moves, identify infeasible workload, preserve completed tasks, and provide undo.
4. **Accessible, stable shell:** resolve hydration mismatch; implement an accessible mobile navigation dialog; verify focus order, keyboard operation, reduced motion, contrast, and narrow layouts.
5. **Better plan comprehension:** show how syllabus text was grouped, daily minutes versus available hours, date-range semantics, and an edit/regenerate path.

### Proposed Version 2 acceptance criteria

- Given a valid fixture provider response, a student can generate a roadmap from setup to dashboard in one uninterrupted flow; the roadmap has exactly the requested study-date range, unique task IDs, and no day exceeds configured capacity.
- Given provider timeout, rate limit, malformed JSON, invalid semantic output, or network failure, the UI shows a specific recoverable state, preserves inputs, prevents duplicate submissions, and does not replace an existing valid roadmap.
- After completing a task, refreshing the page restores the completion state. A documented export/import or authenticated sync path restores the same state on another browser/device.
- Rebalance displays a preview before mutation, never silently places work beyond capacity, reports any infeasible remainder, preserves completed tasks, and supports undo.
- The next actionable day—not simply array index zero—is shown as the focus day, and date calculations use a documented timezone policy.
- Keyboard users can operate setup, task checkboxes, mobile navigation, quick explanation, timer, rebalance preview, and undo. The mobile drawer has an accessible name, dialog semantics, focus return, and Escape-to-close.
- No hydration mismatch appears in a production-like browser run, and a browser smoke test covers setup validation, loading, generation success fixture, generation failure, task completion, persistence, and rebalance.
- README documentation describes setup without exposing secrets, required environment variables by name only, available scripts, known local-storage limitations, and the validation workflow.

## 8. Five most important findings

1. **The core value moment is not reliably completable.** The browser’s valid generation attempt returned 502, and there is no local fixture/demo path for validating the experience independently of the provider. Evidence: browser run, route error handling, and the only seven route tests.
2. **The roadmap contract is structurally strict but semantically permissive.** It checks arrays and field types but not date range, order, IDs, or capacity. Evidence: `isRoadmapResponse` in [route.ts](../src/app/api/generate-roadmap/route.ts).
3. **Adaptive rescheduling can create an unrealistic final day.** Overflow is appended to the last day after earlier capacity is filled, with no preview or feasibility warning. Evidence: `rebalancePlan` in [page.tsx](../src/app/page.tsx).
4. **Progress persistence is browser-local and silent.** It is useful for a prototype but does not meet a dependable multi-session/product promise. Evidence: `localStorage` effects and restore logic in [page.tsx](../src/app/page.tsx).
5. **The shell has an observable theme hydration issue and mobile accessibility gaps.** Evidence: development browser console warning, [layout.tsx](../src/app/layout.tsx), [theme-provider.tsx](../src/app/theme-provider.tsx), and the mobile navigation markup in [page.tsx](../src/app/page.tsx).

## 9. Three highest-priority improvements

1. **Generation reliability and semantic validation** — because no roadmap means no downstream journey.
2. **Capacity-aware rebalance with preview and undo** — because the advertised adaptive behavior can otherwise reduce trust at the moment students need help.
3. **Durable, visible progress persistence** — because completion tracking only creates product value when students can safely return to it.

## 10. Evidence boundaries and real-user validation

This review contains no interviews, quotes, analytics, classroom feedback, or claims about learning outcomes. The assumption map explicitly marks hypotheses that require real students. Technical tests demonstrate behavior of code and fixtures; they do not establish that students understand the copy, trust AI task quality, prefer the timer, or benefit from streaks.
